# FHIR draft technical review

Review date: 2026-10-01. These findings concern source accuracy and reproducibility before authoring. They are not rewritten lesson content. Line numbers refer to the original attachment. Official specifications and read-only metadata/property lookups support the confirmed findings below. No commands from the attachment were executed, no resources were written to public servers, no patient records were retrieved and no full FHIR validator was run.

## Confirmed corrections

| ID | Source lines | Finding and required correction | Primary evidence |
| --- | --- | --- | --- |
| T01 | 174, 181-189, 193, 206 | Conditional create needs POST to the resource type plus `If-None-Exist`. A search in the POST URL does not implement it. Transaction entries use `request.ifNoneExist`. | [R4 conditional create](https://hl7.org/fhir/R4/http.html#ccreate), [Bundle request](https://hl7.org/fhir/R4/bundle.html) |
| T02 | 199-200 | Multiple conditional-create matches produce 412 and require diagnosis. A failed transaction returns one OperationOutcome, not an entry-by-entry transaction-response Bundle. | [R4 REST](https://hl7.org/fhir/R4/http.html) |
| T03 | 193 | Existing resource references can be valid transaction references. The universal prohibition on `Patient/123` is wrong. | T04 | 49, 77, 86 | Resource `id` and `meta` are optional. A `meta.profile` declaration is not proof of validation; absence does not imply automatic US Core rejection. | [Resource definitions](https://hl7.org/fhir/R4/resource.html), [validation](https://hl7.org/fhir/R4/validation.html) |

| T06 | 14 | The claim that HAPI always returns 400 without Accept is too broad. A read-only GET of `/metadata` without that header returned 200 in this review. This does not test every operation. | `verification-review.json`, [R4 REST](https://hl7.org/fhir/R4/http.html) |

| T12 | 529-545 | Posting a document Bundle is not a transaction that stores every contained resource independently. Do not promise that a later Composition search will find an ingested entry. | T17 | 666-674 | Bulk export kickoff needs the asynchronous request convention, including `Prefer: respond-async`. | T19 | 761-768 | Subscription example omits required `reason`. Requested/active status handling and payloads depend on the server; do not assert a universal Bundle payload or one-minute delivery guarantee. | [R4 Subscription](https://hl7.org/fhir/R4/subscription.html) |
| T20 | 807-829, 839-842 | Consent needs policy or policyRule under ppc-1. `provision` is an object with recursive child provisions, not a top-level array. FHIR does not establish the draft's universal conflict rule or automatic enforcement. | [R4 Consent](https://hl7.org/fhir/R4/consent.html) |

## Local and read-only checks actually performed

The nine JSON fences were parsed locally: seven parse, two fail; five parsed examples have resourceType and two are datatype fragments. Parse success is not an R4 validation pass. Subscription and Consent structural failures above were identified by specification comparison, not a validator run. No claim of complete conformance is made.

GET `/metadata` returned 200 at all five referenced service bases (HAPI, Firely, SMART Health IT, Bulk Data, Ontoserver). Metadata reported FHIR 4.0.1 except SMART Health IT, which reported 4.0.0. The exact software versions and relevant declared capabilities are recorded in `verification-review.json`. Capability declarations do not prove task success, authorization, stock datasets or automatic reservation/notification behavior.

NLM RxNorm property lookups confirmed the two medication-code findings. No replacement drug code was invented. Source code fragments containing patient identifiers were analyzed locally and not posted to any endpoint.

This is a pre-authoring review, not `npm run validate`, a site build, a click test or a live course verification. Those checks require the content/application implementation after outline review.
